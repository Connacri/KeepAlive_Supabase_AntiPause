# Supabase KeepAlive — recréer la solution

Application Windows en **un seul fichier Python** (`supabase_keepalive.py`, bibliothèque standard + `pystray` et `pillow` pour l'icône de notification). Elle pinge périodiquement plusieurs projets Supabase gratuits pour éviter la pause après environ 7 jours d'inactivité.

Inspiration : le dépôt `travisvn/supabase-inactive-fix` (MIT). Même principe (insérer, surveiller, supprimer dans une table), mais avec interfaces graphiques et exécution locale.

## Étape 0 — Cadrer avec l'utilisateur

Ne pose des questions que si c'est indispensable. Valeurs par défaut raisonnables : Windows 10/11, Python 3 installé, un ping toutes les 12 h.

À demander seulement si l'information manque :
- Python est-il installé ? (sinon : fournir `creer_exe.bat` basé sur PyInstaller, ou lui dire d'installer Python avec « Add to PATH »)
- Préfère-t-il la **clé publishable/anon** (simple) ou la **clé secrète** (plus sûr côté Supabase) ? Par défaut, proposer les deux variantes de SQL.

Ne jamais demander les clés dans la conversation : elles se saisissent dans l'interface de l'app.

## Livrables à produire

1. `supabase_keepalive.py` — l'application complète
2. `installer.bat` — vérifie Python, `pip install pystray pillow`, lance `pythonw supabase_keepalive.py`
3. `creer_exe.bat` — optionnel, PyInstaller `--onefile --noconsole`
4. `sql_cle_anon.sql` et `sql_cle_secrete.sql` — à exécuter une fois par projet dans le SQL Editor de Supabase

Écrire les `.bat` avec fins de ligne CRLF (`sed -i 's/$/\r/'`) et `chcp 65001`. Livrer avec `present_files`.

## Principe de fonctionnement

Chaque ping fait quatre opérations sur la table `keepalive_pings` via l'API REST (PostgREST) :

1. **INSERT** une ligne (`label`, `note`), avec `Prefer: return=representation` pour récupérer l'`id`
2. **UPDATE** cette ligne (`PATCH ?id=eq.<id>`, `Prefer: return=minimal`)
3. **COUNT** : `GET ?select=id&order=id.asc&limit=1` avec `Prefer: count=exact`, lire `Content-Range` (`0-0/N`)
4. **DELETE** les plus anciennes lignes au-delà de `keep` (5 par défaut) : `GET ?select=id&order=id.asc&limit=<N-keep>` puis `DELETE ?id=in.(1,2,3)`

Le ping est un **succès si l'INSERT réussit** (vraie écriture en base). Un échec d'UPDATE ou de DELETE est signalé dans le statut mais ne fait pas échouer le ping.

### En-têtes HTTP (point important)

- Toujours `apikey: <clé>`
- Si la clé **ne commence pas par `sb_`** (ancienne clé JWT `eyJ…`), ajouter aussi `Authorization: Bearer <clé>`
- Si la clé commence par `sb_` (nouvelles clés `sb_publishable_…` / `sb_secret_…`), **ne pas** l'envoyer en Bearer
- Clé utilisée = clé secrète si renseignée, sinon la clé anon/publishable

### Messages d'erreur lisibles à produire

| Cas | Message |
|---|---|
| `Invalid API key`, JWT, `PGRST301` | Clé API invalide ou expirée |
| 401/403 ou code `42501` | Écriture refusée (RLS) : exécuter le SQL d'aide ou utiliser la clé secrète |
| 404, `PGRST205`, `42P01` | Table introuvable : exécuter le SQL d'aide |
| `PGRST204`, `42703` | Colonne manquante : ré-exécuter le SQL |
| HTTP ≥ 500 | Projet en pause ou indisponible |
| `URLError` | Connexion impossible (réseau ou projet en pause) |
| `KeyError`/`IndexError` sur la réponse | Réponse inattendue (table sans colonne `id` ?) |

Utiliser `urllib` (pas `requests`) pour limiter les dépendances. Timeout 30 s.

## SQL à fournir (par projet)

Commun aux deux variantes :

```sql
create table if not exists public.keepalive_pings (
  id bigint generated by default as identity primary key,
  label text check (char_length(label) <= 80),
  note text check (char_length(note) <= 200),
  created_at timestamptz not null default now(),
  updated_at timestamptz
);

-- Garde-fou : la table ne dépasse jamais 200 lignes
create or replace function public.keepalive_cap() returns trigger
language plpgsql as $$
begin
  delete from public.keepalive_pings
  where id in (select id from public.keepalive_pings order by id desc offset 200);
  return null;
end $$;
drop trigger if exists keepalive_cap_trg on public.keepalive_pings;
create trigger keepalive_cap_trg after insert on public.keepalive_pings
  for each statement execute function public.keepalive_cap();

alter table public.keepalive_pings enable row level security;
```

- **Variante A (clé anon, simple)** : ajouter
  ```sql
  drop policy if exists "keepalive_anon_all" on public.keepalive_pings;
  create policy "keepalive_anon_all" on public.keepalive_pings
    for all to anon, authenticated using (true) with check (true);
  ```
  Expliquer à l'utilisateur : toute personne détenant la clé anon (publique par nature) peut écrire dans cette table seulement, limitée à 200 lignes.
- **Variante B (clé secrète, plus sûr)** : RLS activée **sans aucune policy** (`drop policy if exists "keepalive_anon_all" …`). La clé secrète contourne la RLS. Prévenir : ne jamais partager cette clé.

## Architecture du code

Un fichier, découpé en blocs :

1. **Constantes** : `APP_NAME="SupabaseKeepAlive"`, `LOCK_PORT=48653` (instance unique), `WEB_PORT=8765` (essayer jusqu'à +10 si occupé), `RETRY_AFTER_FAIL_SEC=1800`, `CHECK_EVERY_SEC=60`. Données dans `%APPDATA%\SupabaseKeepAlive\` (`config.json`, `keepalive.log`). Variable d'environnement `KEEPALIVE_DATA_DIR` pour surcharger (utile aux tests).
2. **Import Tkinter protégé** (`try/except`, drapeau `HAVE_TK`) pour permettre le mode sans fenêtre.
3. **Chiffrement des clés** (Windows DPAPI via `ctypes`) : `CryptProtectData` / `CryptUnprotectData`, résultat préfixé `dpapi:` + base64 ; repli `plain:` + base64 hors Windows. Seuls `anon_key` et `secret_key` sont chiffrés. Écriture de `config.json` atomique (`.tmp` puis `os.replace`).
4. **Journal** : fichier rotatif (> 500 Ko → `.old`), fonction `tail_log(n)`.
5. **Démarrage avec Windows** : valeur `SupabaseKeepAlive` dans `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` (module `winreg`), commande `"pythonw.exe" "chemin\script.py" --background` (ou `"app.exe" --background` si gelé par PyInstaller, détecté avec `sys.frozen`).
6. **`ping_project(p)`** : séquence décrite plus haut → `(ok, message)` avec un message du type `OK · INSERT ✓ · UPDATE ✓ · DELETE ✓ (1) · 5 ligne(s)`.
7. **`normalize_project(d, existing=None)`** : validation et nettoyage.
   - URL : doit matcher `^https?://[^/\s]+$` après retrait de `/rest/v1` ou `/rest` final
   - Clés : regex `^[A-Za-z0-9_\-\.=+/]{10,}$` (évite l'injection d'en-têtes). **`None` = clé inchangée, `""` = clé effacée.** Au moins une clé requise
   - Table : `^[A-Za-z0-9_\-]{1,63}$`, défaut `keepalive_pings`
   - `keep` : entier borné 1 à 150, défaut 5
   - Nom : par défaut le nom d'hôte de l'URL
   - **Compte** (`account`, texte libre, 120 caractères max) : le compte Supabase (email ou nom) auquel le projet est lié. Optionnel, `None` = inchangé. Sert à s'y retrouver quand l'utilisateur a plusieurs comptes gratuits
8. **Classe `Core`** (indépendante de l'interface) : config, liste des comptes existants (`accounts()`, triée, sans doublon), libellé de journal `nom (compte)`, verrou `RLock`, file d'événements `queue.Queue` pour la fenêtre Tk, CRUD projets, `import_projects`, `set_settings`, `ping_one`, `ping_many(ids)` (bloquant, verrou `ping_lock`), `ping_async`, planificateur.
9. **Serveur web** (`ThreadingHTTPServer` sur `127.0.0.1` uniquement) + page HTML embarquée.
10. **Fenêtre Tkinter** (`ProjectDialog`, `App`) + icône `pystray`.
11. **`main()`** et gestion d'instance unique.

### Planificateur (rattrapage après veille)

Boucle toutes les 60 s, attente initiale de 15 s au démarrage (le réseau n'est pas toujours prêt). Un projet actif est « dû » si :
- `now - last_ok >= interval_hours * 3600`, **et**
- `now - last_attempt >= 1800` (nouvel essai 30 min après un échec)

Cette logique fait que, si le PC était éteint ou en veille, les pings en retard partent au réveil. Champs mémorisés par projet : `last_ok`, `last_attempt`, `last_status`. Un seul ping à la fois (`ping_lock.acquire(blocking=False)` dans le planificateur).

### Modes de lancement

| Argument | Effet |
|---|---|
| (aucun) | ouvre la fenêtre |
| `--background` | démarre caché dans la zone de notification (utilisé au démarrage de Windows) |
| `--headless` | sans fenêtre, interface web seulement (aussi utilisé si Tkinter est absent) |
| `--once` | pinge tous les projets une fois, affiche `OK`/`ECHEC`, code de sortie 0/1 (Planificateur de tâches) |

Instance unique : `socket.bind(("127.0.0.1", 48653))`. Si le port est pris, se connecter et envoyer `show` pour que l'instance existante affiche sa fenêtre, puis quitter. Ne pas appliquer ce verrou en mode `--once`.

Fermer la fenêtre la masque (si `pystray` disponible, sinon la réduit). Menu de la zone de notification : Ouvrir la fenêtre, Interface web, Pinger maintenant, Quitter. Les callbacks du tray ne touchent jamais Tk directement : ils déposent des événements dans la file lue par `root.after(300, poll_events)`.

## Création automatique de la table à l'ajout d'un projet

PostgREST ne peut pas exécuter de DDL : la table se crée via l'**API de gestion Supabase** avec un **jeton d'accès de compte** (`sbp_…`, Dashboard → Account → Access Tokens).

- Champ optionnel `access_token` par projet (chiffré DPAPI comme les clés, jamais renvoyé par `/api/state`, seulement `token_hint` et `has_token`). `token_for(p)` réutilise le jeton d'un autre projet du **même compte** (casse ignorée) : un seul jeton à saisir par compte.
- `setup_table(p, token)` : `POST {MGMT_API}/v1/projects/<ref>/database/query` avec `{"query": build_sql(table, variant)}`, `Authorization: Bearer <jeton>`. `ref` = premier libellé du host `xxxx.supabase.co` (sinon erreur claire). Variante `secret` si une clé secrète est saisie, sinon `anon`. `MGMT_API` surchargeable par `KEEPALIVE_MGMT_API` (tests).
- `build_sql(table, variant)` remplace les constantes SQL : identifiants entre guillemets (`TABLE_RE` garantit `[A-Za-z0-9_-]`), fonction/trigger nommés par table (`keepalive_cap` / `keepalive_cap_trg` pour la table par défaut, `keepalive_cap_<table>` sinon), et `notify pgrst, 'reload schema';` en dernière ligne.
- **Auto-réparation dans `ping_one`** : si le ping échoue avec « Table … introuvable », « Écriture refusée (RLS) » ou « Colonne manquante » (`needs_setup`), et qu'un jeton est disponible → `setup_table`, pause 2 s (schéma PostgREST), un seul nouvel essai ; succès affiché `OK · table créée · …`. Sans jeton, le statut ajoute « renseigne un jeton d'accès Supabase pour la créer automatiquement ». Donc l'ajout d'un projet crée la table dès le premier ping.
- Bouton « 🛠 Créer la table » (Tk) / 🛠 (web) / `POST /api/projects/<id>/setup` : crée maintenant. Sans jeton : copie le SQL de la table du projet et ouvre `https://supabase.com/dashboard/project/<ref>/sql/new`.
- `/api/sql?variant=…&table=…` (table validée par `TABLE_RE`, sinon table par défaut).
- Erreurs lisibles : 401 jeton invalide/expiré, 403 jeton sans droit sur le projet (mauvais compte), 404 projet introuvable pour ce jeton, 429 trop de requêtes.
- Prévenir l'utilisateur : le jeton donne un accès large au compte Supabase (le garder secret, le révoquer ensuite si besoin).

## Vider la table de keep-alive (un projet ou tous)

- `empty_table(p)` : compte les lignes (`GET … Prefer: count=exact`), puis `DELETE {rest}?id=not.is.null` (PostgREST refuse un DELETE sans filtre ; « id non nul » = toutes les lignes) avec la clé secrète si présente, sinon l'anon. Retourne `(ok, message)` : « vidée (N ligne(s) supprimée(s)) », « déjà vide », ou l'erreur via `describe_error`. Ne recrée jamais la table (pas d'auto-réparation ici) ; ne touche qu'à la table configurée du projet.
- `Core.empty_project(pid)` / `Core.empty_many(ids=None)` (tous les projets, **désactivés inclus**) : sérialisés avec les pings par `ping_lock` (qui est un `Lock` simple : ne jamais appeler `ping_one` ni reprendre le verrou depuis `_empty_one`). Le projet passe en témoin « busy » pendant l'opération ; après succès, « · N ligne(s) » à la fin du dernier statut devient « · 0 ligne(s) (vidée) ». Le vidage n'envoie pas de ping.
- API : `POST /api/projects/<id>/empty` et `POST /api/empty`, qui exigent `{"confirm": true}` (booléen strict, sinon 400) en plus du jeton de session. L'UI web et Tk demandent une confirmation et avertissent si le nom de la table n'est pas `keepalive_pings` (champ `table` modifiable : protège d'un vidage d'une vraie table par erreur).
- UI : menu « 🧹 Vider ▾ » (Tk : sélection / tous, exécuté dans un thread, résultat dans le journal) ; web : 🧹 par ligne + « Vider toutes les tables ».

## Témoins de surveillance (bureau, web, zone de notification)

Fonction commune `health(p, interval_h, now, busy)` → `(niveau, libellé)` : `off` (désactivé) · `busy` (ping en cours, ids dans `Core.busy`) · `err` (dernier ping échoué, ou aucun succès depuis plus de 5 jours = risque de pause) · `new` (jamais pingé) · `warn` (succès plus vieux que 1,5 × l'intervalle, ou une étape UPDATE/DELETE en échec) · `ok`. `Core.public()` expose `health`, `health_label` ; `Core.summary()` compte les niveaux et donne le pire état.

Couleurs : ok `#2ecc71`, warn `#f5a623`, err `#e5484d`, busy `#3b82f6`, new `#8b95a1`, off `#555c64`.

- **Widget de bureau** (`DesktopWidget`, Tk `Toplevel` sans bordure `overrideredirect`, alpha 0,95) : une pastille ronde (`Canvas`) par projet, groupés par compte, « il y a X min », compteur `OK/N` coloré par le pire état. Déplaçable à la souris (position mémorisée dans `config.json` → `widget.x/y`, ramenée à l'écran si hors écran), clic droit : tout pinger / ouvrir la fenêtre / interface web / « Toujours au-dessus » (défaut oui) / masquer. Survol = détail du statut. Re-rendu sur l'événement `refresh` et toutes les 30 s. Config : `widget = {enabled, topmost, x, y}`, par défaut activé. Case « Témoins sur le bureau » dans la fenêtre, entrée de menu dans la zone de notification, et `widget` dans `POST /api/settings`. Le widget est créé même en `--background` (fenêtre principale cachée).
- **Fenêtre principale** : colonne « État » (`● OK`, `● Attention`, `● Erreur`…), lignes colorées par niveau.
- **Interface web** : carte « Surveillance » en tête (tuiles avec LED CSS, légende, résumé `N/M OK`), LED dans le tableau, rafraîchie toutes les 5 s.
- **Icône de notification** : pastille d'état dessinée avec PIL dans le coin de l'icône, couleur du pire état ; infobulle `N/M OK`.
- Les événements `widget`, `togglewidget`, `refresh` passent par la file `core.events` (jamais de Tk depuis un autre thread).

## Interface web locale (`http://127.0.0.1:8765`)

Une seule page HTML embarquée dans le script (CSS et JS inline, thème clair/sombre automatique, responsive). Fonctions : formulaire ajout/modification (champ **Compte Supabase** avec `<datalist>` des comptes existants), tableau des projets **trié par compte** avec colonne Compte et boutons ping / modifier / activer-désactiver / supprimer, boutons de copie du SQL (A et B), réglages, import JSON, journal, rafraîchissement toutes les 5 s.

**Remplissage en vrac** (très apprécié) : un `textarea` où l'utilisateur colle l'URL et les clés. Extraire par regex : URL `https?://[a-z0-9-]+\.supabase\.co`, `sb_publishable_…`, `sb_secret_…`, et pour les JWT `eyJ…` décoder la partie centrale (base64url) et lire `role` (`anon` ou `service_role`) pour classer la clé.

### API (JSON, en-tête `X-Token` obligatoire)

| Méthode | Chemin | Rôle |
|---|---|---|
| GET | `/` | page HTML (le jeton est injecté à la place de `__TOKEN__`) |
| GET | `/api/state` | réglages, liste `accounts`, projets (champ `account` inclus ; clés **jamais** renvoyées, seulement un aperçu de 12 caractères), 30 dernières lignes du journal |
| GET | `/api/sql?variant=anon\|secret` | SQL d'aide |
| POST | `/api/projects` | ajoute et lance un premier ping |
| PUT | `/api/projects/<id32hex>` | modifie (clé absente = conservée) |
| DELETE | `/api/projects/<id32hex>` | supprime |
| POST | `/api/ping` | `{id}` ou tout |
| POST | `/api/settings` | `interval_hours`, `autostart` |
| POST | `/api/import` | `{text: "<JSON>"}` |

Erreurs de validation → HTTP 400 `{"error": "..."}`.

### Sécurité du serveur web (obligatoire)

- Écouter **uniquement** sur `127.0.0.1`
- Jeton aléatoire par lancement (`secrets.token_urlsafe(24)`), comparé avec `secrets.compare_digest`
- Refuser toute requête dont l'en-tête `Host` n'est pas `127.0.0.1`, `localhost` ou `::1` (anti DNS rebinding) → 403
- En-têtes de réponse : `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`
- Échapper tout texte dynamique côté JS (fonction `esc()`), limiter la taille des corps de requête (1 Mo)

## Tests à faire avant de livrer

On ne peut pas tester Windows depuis le conteneur Linux. Tester ce qui est testable :

1. `python3 -m py_compile supabase_keepalive.py`
2. **Faux serveur PostgREST** local (`ThreadingHTTPServer` sur un port libre) qui gère POST (201 + liste), PATCH (204), GET avec `Prefer: count=exact` (renvoyer `Content-Range: 0-0/N`), `DELETE ?id=in.(…)` (204), et rejette une mauvaise `apikey` (401 `Invalid API key`). Vérifier :
   - 5 pings avec `keep=3` → 3 lignes restantes, avec 2 DELETE
   - clé invalide, table absente, serveur éteint → bons messages
3. **API web** (avec `KEEPALIVE_DATA_DIR` pointant vers un dossier temporaire) : page 200, 401 sans jeton, 403 avec mauvais `Host`, ajout, URL invalide → 400, modification sans resaisir la clé (clé conservée), compte conservé lors d'un simple changement d'état, liste `accounts` sans doublon, désactivation, ping, import au format travisvn, suppression, et vérifier que les clés n'apparaissent **ni** dans `/api/state` **ni** en clair dans `config.json`

Dire clairement à l'utilisateur ce qui n'a **pas** pu être testé : la fenêtre Tkinter, l'icône de notification, la clé de registre de démarrage et le chiffrement DPAPI.

## Points à expliquer à l'utilisateur dans la réponse finale

- **Table dédiée conseillée** : un simple appel à la racine de l'API ne compte pas forcément comme activité de base de données ; une écriture réelle est la méthode la plus fiable. Ne pas affirmer qu'une méthode précise est garantie par Supabase.
- **Le PC doit être allumé** : s'il reste éteint plus d'une semaine, les projets se mettent en pause. Alternative sans PC : le workflow GitHub Actions du dépôt `travisvn/supabase-inactive-fix` (gratuit, lundi et jeudi) ; peut être utilisé en complément.
- **Un projet déjà en pause** ne se réveille pas par un ping : le restaurer à la main dans le tableau de bord Supabase.
- **Choix de clé** : variante A (anon, simple, table écrivable par tout détenteur de la clé anon) ou variante B (clé secrète, plus sûr côté Supabase, clé chiffrée localement par DPAPI). Conseiller la B si l'utilisateur est à l'aise.
- Ne pas déplacer ou supprimer le dossier de l'app après installation (le démarrage Windows pointe vers le script).
- Si un projet apparaît en rouge : lire le statut, il indique s'il manque le SQL, si la clé est refusée ou si le projet est en pause.

## Pièges rencontrés

- Les clés `sb_publishable_` / `sb_secret_` ne sont pas des JWT : ne pas les envoyer dans `Authorization: Bearer`.
- Une clé collée avec un retour à la ligne casse les en-têtes HTTP : toujours `strip()` et valider par regex.
- Dans l'interface web, ne jamais renvoyer les clés complètes au navigateur ; à la modification, un champ vide veut dire « garder la clé actuelle ».
- Les callbacks de `pystray` s'exécutent dans un autre thread : passer par une file d'événements pour toucher à Tkinter.
- Après le démarrage de Windows le réseau peut ne pas être prêt : attendre une quinzaine de secondes et réessayer 30 minutes plus tard en cas d'échec.
- Python `urllib` lève une exception sur les codes HTTP d'erreur : attraper `HTTPError` et lire son corps pour décoder le code PostgREST (`PGRST205`, `42501`…).
- Sur Windows, utiliser `pythonw.exe` (pas `python.exe`) pour le démarrage automatique, sinon une console reste ouverte.
- Un `time.sleep` patché globalement dans un test casse aussi les attentes du test lui-même : remplacer seulement le `time` vu par le module testé.
- Tkinter n'est pas installable dans le conteneur : valider le code GUI avec un faux module `tkinter` (classes factices) pour attraper les erreurs de nom, et dire clairement que le rendu réel (widget de bureau, icône) n'est pas testé.
